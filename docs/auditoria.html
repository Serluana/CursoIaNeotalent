Hallazgos por severidad

Filtra la lista para revisar primero los riesgos que bloquean la publicación. La búsqueda encuentra palabras dentro del título y la explicación.

Alto

XSS almacenado o inyección de HTML

Los campos de los tickets entran directamente en innerHTML sin escape. Un título manipulado puede convertirse en HTML o JavaScript.

Alto

Overflow horizontal a 768 px

La cola mantiene cinco columnas de mínimo 150 px: necesita 798 px antes de contar el padding del tablero.

Medio

Material interno accesible

Publicar la raíz completa expondría documentación, tests, instrucciones, mockup y material de referencia que la app no necesita.

Medio

Dataset y persistencia local públicos

Los 60 tickets se descargan completos y las altas viven en localStorage, sin autenticación ni control de acceso.

Medio

Diferencias con la especificación

La demo no implementa IA, asignación, detección real de duplicados ni persistencia de decisiones como describe el spec.

Medio

Local y Surge no son el mismo escenario

La ruta relativa funciona por HTTP desde la raíz, pero abrir el archivo directamente puede fallar por módulos ES y fetch.

Bajo

No hay secretos detectados

La búsqueda literal no encontró claves, contraseñas, tokens ni autorización. Sí hay una marca de terceros que conviene autorizar.

02 · Superficie pública

Seguridad y exposición

La amenaza principal en una app estática no es un backend atacable: es publicar datos, contexto o contenido ejecutable que no debía salir.

Lo comprobado frente a lo interpretado

Comprobado No aparecen coincidencias literales de password, secret, claves API, tokens o Authorization. Esto no equivale a una auditoría criptográfica ni de historial Git.

Comprobado El JSON contiene datos de demostración y el README declara que son inventados.

Interpretación Si los datos fueran sustituidos por tickets reales, Surge no ofrecería privacidad: cualquier visitante podría descargar data/tickets.json.

Corrección urgente del renderizado

Usar nodos DOM y textContent, o un escape HTML centralizado, para todos los valores procedentes del ticket. required solo comprueba que hay contenido; no lo hace seguro.

// Dirección recomendada: texto, no HTML interpretado.
const title = document.createElement("div");
title.className = "value";
title.textContent = selectedTicket.titulo;
detailEl.append(title);

Otros problemas de despliegue
  • Carga: response.ok no se comprueba antes de response.json(); un 404, HTML o JSON inválido acaba en el mismo error genérico.
  • Guardado: localStorage.setItem no está protegido contra cuota llena, modo privado o políticas del navegador.
  • Rutas: las referencias son relativas y deberían funcionar en la raíz servicedesk-grupo-N.surge.sh; no hay router ni rutas internas.

Plan de 30 minutos

Arreglos rápidos antes de publicar

La lista está ordenada por impacto: primero impedir contenido ejecutable y desbordamientos; después reducir la superficie pública y alinear expectativas.

  1. Eliminar la inyección HTML con textContent o escape centralizado y añadir un test con un título malicioso.
  2. Corregir tablet y barra móvil; probar exactamente 375, 768 y 1440 px.
  3. Crear .surgeignore o publicar un directorio mínimo.
  4. Confirmar que el JSON sigue siendo sintético; nunca subir tickets reales a Surge.
  5. Comprobar response.ok, capturar errores de localStorage y persistir decisiones si son requisito.
  6. Describir la clasificación como heurística local mientras no exista integración de IA.
  7. Confirmar permiso para usar la marca Verisure o sustituirla.

Conclusión: la app puede servirse como demo estática desde la raíz de Surge, pero no debería publicarse aún sin corregir el renderizado sin escape y el overflow de tablet. Esta página no crea .surgeignore ni ejecuta Surge.
